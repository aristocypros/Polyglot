Polyglot

A multi-chain HD wallet signing service that only signs what your policy engine has signed first. The API and database are treated as hostile; keys live behind a PKCS#11 HSM and a Rust signer with no open ports.

What it is

Signing middleware for custody workflows

Institutions that hold crypto assets need a service that turns "this transfer is approved" into a valid blockchain signature, across many chains, without trusting every system in between. Polyglot is that service.

It creates HD wallets, derives keys by path on demand, and signs raw transactions for Bitcoin, Ethereum and EVM networks, Solana, Tron and the XRP Ledger. It does not decide what is allowed. Your policy engine makes that call and signs the request; Polyglot checks that signature itself and refuses anything else.

The prototype is vendor-neutral: it uses only standard PKCS#11, so moving from SoftHSMv2 to Utimaco, CloudHSM or YubiHSM2 is a change of four config values.

Architecture

Two trust zones, one direction of trust

Three services and a one-shot bootstrap job run in Docker Compose. The signer has no inbound ports and no internet route. It reaches out to the API to claim work.

Can delay or drop requests, cannot sign Only place a signature can be produced
Request lifecycle

How one signature gets made

Every operation (create_wallet, derive_public, sign) is asynchronous. The client submits, then polls.

  1. Client → policy engine
    The client builds a canonical JSON body (RFC 8785). The policy engine evaluates it and, if allowed, signs those exact bytes with Ed25519 or ES256.
  2. Client → API
    POST /v1/requests with the envelope. The API checks shape and size only, stores it as ready, and returns 202.
  3. Signer → API
    The signer long-polls /internal/claim. Postgres hands out the next request with FOR UPDATE SKIP LOCKED and a 60-second lease.
  4. Signer
    Runs the 9-step verification checklist below. Any failure ends the request with zero signatures.
  5. Signer → HSM
    Unwraps the seed with C_Decrypt, derives the child key, loads it as a short-lived session object, calls C_Sign, then destroys it and wipes memory.
  6. Signer → API
    Signs its own response with its Ed25519 identity key, stores it, and posts it to /internal/results.
  7. Client
    GET /v1/requests/{id} returns the result. The client verifies signer_sig against the key published at GET /v1/signer.

    Cryptography

    How a seed is stored

    At wallet creation the HSM generates a 64-byte seed with C_GenerateRandom. It is wrapped with CKM_AES_GCM under kek-v1 using a fresh 12-byte IV, and the 92-byte result is stored in app.wallets.

    IV12 B
    ciphertext64 B · bytes 12–76
    tag16 B

    The wrap is bound to its wallet by associated data. The signer builds it from the verified request body, so a blob copied from another wallet fails to decrypt.

    The signer refuses to start unless a startup probe passes: the PKCS#11 library loads, AES-GCM round-trips and rejects tampering, the KEK has the right attributes, published BIP32 and SLIP10 vectors match, and a throwaway session key signs and leaves no objects behind.

    Derivation

    From one seed to a key on each chain

    A wallet holds one 64-byte seed. Each chain's key is found by walking a path from that seed, one level at a time. Pick a chain to follow its path, using the paths from make demo.

      Five chains, decoded before signing

      Limits of the generic tier

      • SoftHSMv2 is software. It shows the exact PKCS#11 flow, not tamper resistance.
      • Standard PKCS#11 has no portable BIP32/SLIP10 derivation, so the seed is decrypted into zeroized signer memory for each request.
      • PKCS#11 has no BIP340 Schnorr mechanism, so Taproot inputs are signed in software and reported as signing_in_hsm: false.
      • Memory hygiene is best effort: zeroized buffers and no core dumps, checked by a heap-scanning test allocator.
      • There is no attestation that the running signer binary is the approved build.

      Certificates

      The prototype uses none. Every hop runs on plain HTTP or plain Postgres inside Docker networks: the signer reaches the API at http://api:8081, and both services connect to Postgres with TLS off. The backend network is internal: true, and integrity comes from signatures rather than transport: the policy engine signs requests and the signer signs responses.

      The spec lists mTLS as the replacement for bearer tokens in a later phase. That will add a CA, a server certificate for the API and a client certificate for the signer and each client.

      Tighten before production

      • SoftHSM PINs are random per install, or set with SOFTHSM_USER_PIN and SOFTHSM_SO_PIN. With a real HSM, use its own credentials and keep the SO PIN off the signer host.
      • The API container receives the admin and signer_role passwords so it can run migrations and set role passwords. A compromised API could then log in as signer_role. Move migrations and role setup into a one-shot job and give the API only its own password.
      • Until the API sets them at first start, the migration creates both roles with default passwords.
      • secrets/pe/*.key are written world-readable (0644). In production these keys live in the client's policy engine, never on this host.
      • The signer identity key is a file on the token volume. A native backend would keep it in the HSM.
      Try it

      Run it on a laptop

      # secrets, policy-engine keys, SoftHSM token and kek-v1
make bootstrap
# start api, signer, postgres
make up
# 2 wallets, 5 chains signed and verified, replay and forgery rejected
make demo
make down

      The demo pins the signer's identity key, signs one transfer each on Ethereum, Solana, Tron, XRPL and Bitcoin (P2WPKH plus Taproot), verifies every chain signature and the decoded summary, then confirms a replay gets 409 and a forged body gets 422 bad_signature. make test runs 196 Rust tests, the Go suite, Python cross-checks over 2,000 random derivation paths and 500 JCS fuzz cases, and a 28-point database permission matrix.

      Scope

      What the prototype covers

      In

      • Wallet creation with HSM-generated, AEAD-wrapped seeds
      • Full-path derivation for BIP32 and SLIP10
      • Public key derivation, digest signing, raw transaction signing
      • Session-object signing in the HSM with flagged software fallback
      • Policy-engine authorization, replay protection, signed responses
      • Vendor conformance suite against the Backend trait
